# Vital 赛道要求清单 · Bilingual Requirements List

Source: Vital_活域_赛制与评审细则 (AIx Origin Summit, updated 2026-08-31)

## 1. 主赛道技术门槛（必须同时满足）· Hard technical gates (all five required)

| 原文 | English |
| --- | --- |
| 可运行门槛：必须提供可访问的 Web / App / 对话 Agent 等原型，现场能走完至少一条完整用户路径。纯 PPT、纯策划、只有渲染图视为未完成。 | Runnable gate: provide an accessible prototype (web, app, or conversational agent) that can complete at least one full user path live on site. Slides only, planning docs only, or renders only count as unfinished. |
| AI 结合要求：AI 必须实质改变理解、生成、推荐、交互或流程组织；固定文案网站、简单表单、只接一个聊天框而不改变关键任务，不构成显著 AI + Soft Healthcare 能力。 | AI integration: AI must materially change understanding, generation, recommendation, interaction, or process organization. A static-copy site, a simple form, or a bolted-on chat box that does not change the key task does not count. |
| 用户路径门槛：Demo 须能指出目标用户是谁、从哪一个具体困扰进入、AI 输出后用户下一步做什么。 | User-path gate: the demo must show who the target user is, which specific trouble they enter from, and what the user does next after the AI output. |
| 合规可见门槛：面向用户的健康相关输出必须有显著免责声明；涉及情绪支持时必须有基础危机识别与转介设计。 | Visible-compliance gate: every user-facing health output carries a prominent disclaimer; anything touching emotional support has basic crisis detection and referral design. |
| 数据门槛：只允许合成数据、公开脱敏数据、团队模拟数据；训练与演示均不得使用未脱敏真实患者资料。 | Data gate: only synthetic, public de-identified, or team-simulated data. Neither training nor the demo may use non-de-identified real patient data. |

## 2. 负面清单 · Negative list (any of these = not accepted)

| 原文 | English |
| --- | --- |
| 只有 App 壳体、只有策划案、只有 PPT / 原型图、现场无法操作 | App shell only, planning doc only, slides or mockups only, or cannot be operated on site |
| 产品名、界面或路演使用「诊断」「治疗」「处方」「治愈」等词汇，或明示替代医护 | Product name, UI, or pitch uses words like "diagnose", "treat", "prescribe", "cure", or explicitly claims to replace medical staff |
| 无免责声明的健康解释 / 陪伴产品 | Health-explanation or companion products with no disclaimer |
| 涉及情绪支持却完全没有危机识别与本地转介设计 | Involves emotional support but has no crisis detection or local referral design at all |
| 上传未评估第三方的可识别健康 / 情绪数据，或隐瞒跨境传输 | Uploads identifiable health or emotional data to unvetted third parties, or hides cross-border transfer |
| 演示真实患者病历或未授权个人信息 | Demos real patient records or unauthorized personal information |

## 3. 评审三问 · Judges' three filter questions

评委打分前先用三问过滤。任一问明显失败，主奖竞争力显著下降。
Judges apply three questions before scoring. Clearly failing any one sharply reduces main-prize competitiveness.

| 原文 | English |
| --- | --- |
| 它真的能实际演示吗？——用户能否在现场走完一条完整路径，而不是只看幻灯片。 | Can it actually be demoed? Can a user complete a full path live, rather than just watching slides? |
| AI 是否真正参与？——去掉模型或 Agent 后，产品是否立刻失去关键能力。 | Is AI genuinely involved? If the model or agent is removed, does the product immediately lose a key capability? |
| 是否有 Soft Healthcare 场景且应用清晰？——用户与痛点是否具体，是否诚实区分支持与治疗，免责与数据说明是否到位。 | Is there a clear Soft Healthcare scenario? Are user and pain point specific, is "support" honestly separated from "treatment", and are disclaimer and data statement in place? |

## 6. 参考方向 · Directions (declare one main direction)

Vital 采用两个主参考方向 + 一个自由方向，三个方向均进入 Vital 主榜。方向意在引导而非强制命题。可融合，但须声明主方向。
Two main reference directions plus one open direction, all on the same leaderboard. Directions guide rather than mandate. Blending is allowed, but you must declare a main direction.

### A｜健康信息赋能与可及性 · Health information empowerment and accessibility（建议做到 · Recommended）

| 原文 | English |
| --- | --- |
| 有明确的信息对象（一类报告、一类说明、一类宣教或一类导航任务），不是「什么病都答」。 | Have a specific information target (one type of report, instruction, education material, or navigation task), not "answers any disease". |
| 可运行解读或交互原型，至少一条完整用户流程可现场走通。 | A runnable interpretation or interaction prototype with at least one complete user flow working live. |
| 输出结构建议包含：通俗解释 + 可行动下一步 + 何时应寻求专业协助。 | Suggested output structure: plain explanation + actionable next step + when to seek professional help. |
| 不建议在无专业证明下生成诊断结论、用药建议或替代专业意见的表述。 | Do not generate diagnostic conclusions, medication advice, or statements replacing professional opinion without professional backing. |

### B｜智能陪伴与行为支持 · Intelligent companionship and behavioral support（建议做到 · Recommended）

| 原文 | English |
| --- | --- |
| 行为建议关注生活方式、习惯养成、情绪记录、提醒与动机支持等非临床层面。 | Behavioral advice stays non-clinical: lifestyle, habit formation, mood logging, reminders, motivation. |
| 不在无专业人士参与下涉及用药调整或疾病管理决策。 | No medication adjustment or disease-management decisions without professional involvement. |
| 凡提供情绪支持对话或记录，必须具备基础危机关键词识别，并转介真实可靠资源。 | Any emotional-support chat or logging must have basic crisis keyword detection and refer to real, reliable resources. |
| 不提供可能加重风险的建议。 | Do not give advice that could increase risk. |

### C｜开放创新 · Open innovation

| 原文 | English |
| --- | --- |
| 需要明确：目标用户、真实痛点、为何属于 Soft Healthcare、如何符合统一合规规则。 | Must clarify: target user, real pain point, why it is Soft Healthcare, how it meets the unified compliance rules. |
| 不建议出现诊断 / 治疗声称；必须有免责声明与数据说明。 | No diagnosis or treatment claims; must have a disclaimer and data statement. |
| 鼓励方向（非强制）：医疗行政软件：文书结构化、患者导航、多语言导诊信息（非分诊诊断） | Encouraged (optional): healthcare admin software: document structuring, patient navigation, multilingual guidance info (not triage diagnosis) |
| 鼓励方向（非强制）：企业 / 社区健康管理的隐私友好方案 | Encouraged (optional): privacy-friendly corporate or community health management |
| 鼓励方向（非强制）：跨 A/B 的融合，例如「可读的出院说明 + 依从提醒」 | Encouraged (optional): A/B blends, e.g. "readable discharge instructions + adherence reminders" |

## 11. 评审与计分 · Judging and scoring

### 评审流程 · Process

| 原文 | English |
| --- | --- |
| 完整性与合规审核：检查可运行性、免责声明、数据说明、情绪方向护栏、赛道匹配。纯 PPT、造假或重大违规直接淘汰。 | Completeness and compliance review: runnability, disclaimer, data statement, emotional-direction guardrails, track fit. Slides only, faking, or major violations are eliminated outright. |
| 现场 Demo 与路演：独立打分，观察完整路径、AI 承重、体验、边界表达。 | Live demo and pitch: scored independently on full path, AI load-bearing, experience, boundary expression. |

### 评分表（100 分）· Rubric (100 points)

| 维度 · Dimension | 权重 · Weight | 评分要点 · Criteria |
| --- | --- | --- |
| 合规、安全与伦理 · Compliance, safety, ethics | 10% | 责任控制、数据最小化、风险控制、透明度、免责声明；B 方向护栏可演示。审核阶段可因缺护栏或诊断声称出局。 · Responsibility control, data minimization, risk control, transparency, disclaimer; direction B guardrails demoable. Missing guardrails or diagnosis claims can eliminate you at review. |
| 问题定义与专业相关性 · Problem definition and professional relevance | 20% | 是否针对真实 Soft Healthcare 痛点；用户画像具体；方案逻辑专业；边界意识。 · Targets a real Soft Healthcare pain point; specific user persona; professional solution logic; boundary awareness. |
| 创新性与用户体验 · Innovation and UX | 30% | 创意亮点、真实可交互、个性化、多模态、包容性设计、路径流畅。 · Creative highlights, real interactivity, personalization, multimodality, inclusive design, smooth path. |
| 原型完成度与可开发性体现 · Prototype completeness and buildability | 20% | 功能可演示、流程完整、技术实现合理、72H+48H 约束下完成度高。 · Demoable features, complete flow, sound technical implementation, high completion within 72H+48H. |
| 落地潜力 · Viability | 20% | 后续迭代或持续推进空间、路演清晰、产品力、孵化前景存在 · Room for iteration, clear pitch, product strength, incubation prospects. |

### 计分原则 · Scoring principles

| 原文 | English |
| --- | --- |
| 每维度 1—10 分，按权重计 100 分。 | Each dimension scored 1 to 10, weighted to 100. |
| 评委满额时去一个最高分与一个最低分后取均值；回避时按有效评委均值。 | With a full panel, drop one highest and one lowest score and average; with recusals, average the valid judges. |
| 平局依次比较：创新性与用户体验 → 问题定义与专业相关性 → 原型完成度。仍相同则无回避评委合议。 | Ties broken in order: innovation and UX, then problem definition, then prototype completeness. Still tied: non-recused judges deliberate. |
| 诊断声称、使用未脱敏真实病历、伪造 Demo、贿票，可一票否决。 | Diagnosis claims, non-de-identified real records, faked demos, or vote-buying can be vetoed by a single judge. |

## 12. 统一强制规则 · Mandatory compliance rules

### 数据 · Data

| 原文 | English |
| --- | --- |
| 只允许合成数据、公开脱敏数据集、团队自行模拟生成的数据。 | Only synthetic data, public de-identified datasets, or team-generated simulated data. |
| 训练中不得使用未脱敏的真实患者健康记录或任何可识别个人的健康资料。 | No non-de-identified real patient health records or any personally identifiable health data in training. |
| 贯彻最少收集：只处理完成可演示功能所必需的数据。 | Data minimization: process only what the demoable function needs. |
| 模拟健康 / 情绪输入须在界面告知并取得模拟同意。 | Simulated health or emotional inputs must be disclosed in the UI with simulated consent obtained. |

### 医疗声称 · Medical claims

| 原文 | English |
| --- | --- |
| 不出现诊断、处方、治疗建议或声称可替代专业医疗人员。 | No diagnosis, prescriptions, treatment advice, or claims of replacing medical professionals. |
| 所有面向用户的输出须附带清晰、显著免责声明。 | All user-facing output carries a clear, prominent disclaimer. |
| 不得在产品名称、界面或宣传中使用「诊断」「治疗」「处方」等词汇。 | No "diagnose", "treat", or "prescribe" in product name, UI, or marketing. |

### 透明度与 Human-in-the-loop · Transparency and human-in-the-loop

| 原文 | English |
| --- | --- |

| 关键或敏感输出应可编辑、可撤回或经模板约束。 | Key or sensitive outputs should be editable, retractable, or template-constrained. |
| Agentic AI 须限制权限并说明，避免过度自动化。 | Agentic AI must have limited, documented permissions; avoid over-automation. |

## 13. 原创与演示真实性 · Originality and demo authenticity
